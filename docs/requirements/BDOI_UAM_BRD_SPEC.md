## 2. Business context

The BRD was written in April 2025 for the legacy **QPS** (Quotation and Pre-processing System), before BIBS. In BIBS it becomes the **system-wide user access maintenance**: every BIBS module uses the same users, roles (the BRD's "group profiles") and permissions. Today the BU asks IT for every access change. The BRD wants the BU to run access itself, with four eyes:
- a **Requestor** submits access requests for new users, changes, deactivations and reactivations, alone or in bulk. Requests can be drafted, corrected when returned, and cancelled. The Requestor chooses the approver;
- an **Approver** approves, rejects or returns the request. The **system** then grants the access;
- a **Business Administrator** requests new, changed, deactivated or reactivated group profiles, approved by one or more approvers. The **System Administrator** then creates or modifies the profile;
- reports: user access, group profile (module / task / access), membership and the access audit log;
- NFRs: authentication against BDO **EUA** with the Windows ID, LDAP / AD / SSO support, lockout after **3** failed attempts, strong passwords, self-service reset, effective-dated changes, bulk updates, notifications, and escalation of risky changes.

BrokerVerse already has most of the core:
- `security`: users, roles, permissions, BCrypt, lockout parameter, session policy, audit of logins;
- `nbadmin`, built for BRD-1 BRNB.085 and BRD-3 PMADD05: access requests (create user, change roles, disable, enable, change role permissions) decided under four eyes and applied on approval, the User Access Matrix (by permission and by area / action class) with Excel export, and data retention.

BRD-11 therefore **extends `nbadmin` and `security`**:
- request lifecycle: draft, return and correction, cancellation, chosen approver(s), group-profile requests with an implementation step, bulk;
- user attributes: Windows ID, business unit, user level, effective date;
- role activation;
- finer permissions per function;
- structured access-change log, session log and logout;
- password policy;
- the directory-authentication seam;
- four reports.

No new business module is needed.

## 10. Observations on the BRD pack

- The BRD is written for **QPS** (April 2025) and predates BIBS. It is read here as the BIBS-wide user access maintenance (UQ19).
- Pages 20-38 repeat pages 1-19 as a scanned, signed printout; page 39 is the e-mail sign-off (28-Apr-2025). No requirement differs between the two copies.
- Duplicate IDs: **BRD 2.002.7.1** is used for "Add remarks" and "Save remarks"; **BRD 3.003.1.1** is used for "User Access Report" and its field "User name".
- Irregular numbering: "V. Reactivate User" is `BRD 1.005` (not 1.005.1) and its sub-steps shift by one level (1.005.1.1 = "1.1 Search", 1.005.1.1.1 = "1.2 Add remarks"). "Add remarks" and "Save remarks" rows often have no scope / mandatory flag, and the System Administrator login rows (4.001.x) have none at all.
- BRD 4.002.2.10 reads "Generate Reports Request function to a specific user profile / role" (the word "Assign" is missing).
- The requirements have no acceptance criteria, no high-risk flags and no NFR IDs; almost every infrastructure NFR is answered "Follow existing QPS set up", and the retention values are "Follow QPS retention policy".
- The p.6 diagram says the **system** grants user access on approval, but the **System Administrator** implements group profiles. BIBS today applies both on approval (UQ03).
- The stakeholder table (p.7) spells "Business Adminitrator"; the functional table uses both "an Business Administrator" and "Business Adminitrator".
- The sample report C is titled "User Group Profile Report", like sample B, but lists members; it is read as the Group Profile Membership list (BRD 3.003.3).
- The sample reports show "Date and Time Generated: 04/14/2025 08:30:145 AM" (invalid seconds) and the author's name as generator; they are layout samples only.
- The NFR "Should able to forward email notification to designated users on failed batch runs" is stated twice (p.15).
- The single-role rule of the Collections NFR (CQ23) conflicts with NFR 1.c-d here (several roles per user allowed).
- The documentation NFR sentence on the user-administration guide is truncated (p.17, UQ18).
- The company is written "BDO Insurance and Brokerage Inc." (p.5) and "BDO Insurance and Brokers Inc." on the sign-off sheet.
