# Security Controls

| Area | Control | Where |
|---|---|---|
| Authentication | BCrypt (cost 12) passwords; user re-loaded on every request so disabling/locking is immediate; one uniform message for a wrong password, a locked and a deactivated account (the real reason is audited and logged) | `security`, `SecurityConfig`, `AuthService` |
| Token model | Access token: JWT HS256 with issuer, expiry, token id (`jti`) and session id (`sid`), valid `ACCESS_TOKEN_MINUTES` (15). Refresh token: 256-bit random value in an HttpOnly, SameSite=Strict cookie limited to `/api/v1/auth`, bound to the sign-in session, replaced on every renewal (only its SHA-256 is stored). A replaced refresh token presented after the 30-second grace ends the session (`TOKEN_REUSED`). The session has an absolute end (`BROKERVERSE_TOKEN_VALIDITY`, 8 hours) and ends after `SESSION_TIMEOUT_MINUTES` without activity (the renewal is not activity); sign-out ends it at once. The web client renews the token in the background, so users are not signed out while working | `SignInSessions`, `JwtTokenService`, `RefreshCookies`, `api/client.ts` |
| Token checks fail closed | A token without a session is refused. When the token denylist (Valkey) cannot be read the session log in PostgreSQL decides (every sign-out also ends the session there); when the session log cannot be read the request is refused with HTTP 503 `SIGN_IN_CHECK_UNAVAILABLE`. Each outage is logged at ERROR, counted in `brokerverse_security_store_failures_total{store}` and raised as the alert `SECURITY_STORE_UNAVAILABLE` | `JwtAuthenticationFilter`, `SecurityStoreAlarm` |
| Second factor | TOTP (RFC 6238, 6 digits, 30 s, one step of drift, a code is never accepted twice) with an authenticator app, asked after the password. Parameter `MFA_POLICY` (security parameter, changed under a second approval): `ALL`, `PRIVILEGED` (roles of privilege level HIGH or ADMIN; delivered value) or `OFF`; a user who enrolled is always asked. Enrolment at the first sign-in (QR code drawn on the server, key in Base32) or on My Profile; ten single-use recovery codes (SHA-256 only). Secrets encrypted with AES-256-GCM, key from the environment (`BROKERVERSE_MFA_ENCRYPTION_KEY`), bound to the user; key rotation with the previous key. Remember-device off (`MFA_REMEMBER_DEVICE_DAYS` = 0). A wrong code counts towards the lockout. An administrator reset needs a second administrator (`MFA_RESET` requests, `MFA_RESET_APPROVE` approves, never the requester), removes the app, the codes and the remembered devices and ends the user's sessions; every step is audited | `security.service.mfa`, `SecondFactorSignIn`, V1181 |
| Single sign-on | `AUTH_MODE` = `OIDC` (authorisation code with PKCE S256, confidential client; ID token signature from the provider's key set, issuer, audience, expiry and nonce checked) or `SAML` (signed Response or Assertion validated with the configured provider key only, one Assertion as a child of the Response, reference to the signed ID and unique IDs against signature wrapping, audience, recipient, validity and InResponseTo; no DTDs). The identity is linked to an existing active user only (never created); optional group gate. The provider's answer is exchanged for a one-time ticket (2 minutes) that the web client redeems. Local passwords only for the break-glass administrators (`BROKERVERSE_SSO_BREAK_GLASS_USERS`), who always need the second factor | `security.service.sso`, `SsoController`, V1182 |
| Password policy | ≥ 10 chars, upper, lower, digit, symbol; history, minimum and maximum age (parameters) | `PasswordChangeRequest`, `AuthPasswordPolicy` |
| Lockout | Consecutive failures (wrong password or wrong second-factor code) up to the business parameter `LOGIN_MAX_FAILED_ATTEMPTS` (maintained under System Parameters) lock the account (`BROKERVERSE_MAX_FAILED_ATTEMPTS`, default 5, only when the parameter is missing); unlock by administrator; all attempts audited | `AuthService`, `SignInCompletion` |
| Rate limits | Per client address: sign-in steps (password, second factor, single sign-on completion) 20 per minute; "Forgot password?" 10 per 15 minutes; reset links 3 per user per 15 minutes (the answer stays the same). The limits use Valkey, the database when Valkey is unreachable, and refuse when neither answers | `LoginRateLimiter`, `LoginRateLimitFilter` |
| Initial administrator | Created only on an empty installation from `BROKERVERSE_ADMIN_INITIAL_PASSWORD`; must change the password at the first sign-in; the password ages like any other | `AdminBootstrap` |
| Authorization | Fine-grained permissions (`Permission`) on every endpoint via `@PreAuthorize`; roles are permission bundles; report catalogue filtered per permission. The system-to-system APIs (`/integration/**`, e.g. the connectivity check) are served only by their own security chain with the API gateway's tokens; a user token is refused there | controllers, `ReportService`, `IntegrationSecurityConfig` |
| Data scope | Each user may act only for his companies and branches: "All companies" (the default of every existing and new user, so a deployment keeps its behaviour until an administrator narrows a scope) or a list of companies, each with all or some of its branches. Fail closed: an unknown user, a user request without a signed-in user and a company or branch outside the scope are refused with HTTP 403 `DATA_SCOPE_DENIED`. Checked centrally before the controller: the `companyId` query parameter and path variable and the `branchId` query parameter (interceptor on `/api/**`), the `companyId` / `branchId` of request bodies and of their item lists (body advice), explicit checks for bodies naming companies otherwise (`@CompanyScoped`). Company lists, the approval inbox, inter-company relationships and consolidation groups show only allowed companies. Exempt: background processing and the system-to-system APIs (`/integration/**`). A scope changes through a user access request (maker-checker) or the audited emergency direct edit, only within the administrator's own scope, never one's own; every change is in the access change log (`DATA_SCOPE_CHANGED`). The build fails when a controller method takes a company that no check reads | `common.security.DataScope`, `DataScopeGuard`, `DataScopeInterceptor`, `DataScopeBodyAdvice`, V1240, `ArchitectureTest`, `DataScopeCoverageIT`, [`DATA_SCOPE_DESIGN.md`](../architecture/DATA_SCOPE_DESIGN.md) |
| Segregation of duties | Administrators cannot post; makers cannot authorize their own journals or master data; authorization limits per user on journals, payables, claims and underwriting approvals (policies, endorsements, quotations), and the approval inbox hides items above the viewer's limit | `AuthorizableEntity`, `JournalBatch.authorize`, `JournalAuthorizationService`, `PayablesSupport`, `ClaimSupport`, `UnderwritingAuthority` |
| Data integrity | Ledger rows immutable (DB trigger); corrections by reversal only; optimistic locking; balanced-journal invariant; gapless document numbers | V1 migration, `JournalBatch`, `DocumentNumberService` |
| Audit | Every create/update/authorize/post/reverse/login/report run/export recorded with user and time, in the same transaction as the change; insert-only in the application (no update/delete API) **and** in the database: triggers reject every `UPDATE`, `DELETE` and `TRUNCATE` on `audit_log` for every client. There is no retention purge; archiving needs the table owner to disable the triggers, on record | `audit`, V26 migration |
| Input validation | Bean Validation on all requests; typed parameters; SQL via bound parameters only | DTOs, repositories |
| Output | RFC 7807 errors; no stack traces or internal messages leaked (an `IllegalArgumentException` answers a generic HTTP 400); the password reset check never returns the user name; the user directory gives other users' role names only to user administrators and auditors; CSV formula-injection protection | `GlobalExceptionHandler`, `CsvReportRenderer`, `UserDirectoryController` |
| Transport & headers | TLS at the gateway (Kubernetes Gateway API) and to the pods; HSTS (one year, sub-domains) from the API and the web server; CSP: `default-src 'none'` on the API answers, and on the web client `default-src 'self'` with `object-src 'none'`, `base-uri 'self'`, `form-action 'self'`, `frame-ancestors 'none'` (`style-src 'unsafe-inline'` remains for the style attributes of the screens); X-Frame-Options, Referrer-Policy no-referrer, nosniff; CORS allow-list. Every dynamic link address passes `safeUrl` (lint rule) | nginx.conf, `SecurityConfig`, `utils/safeUrl.ts` |
| API documentation | springdoc (`/v3/api-docs`, `/swagger-ui`) only on a developer's machine (`BROKERVERSE_ENVIRONMENT=local`) or with the `dev` profile | `ProductionSafeguards` |
| Metrics | Prometheus metrics on the management port (`BROKERVERSE_MANAGEMENT_PORT`, 9090 in Kubernetes) without a user token, reachable from the `monitoring` namespace only (NetworkPolicy `allow-monitoring`); on the application port they need `METRICS_VIEW` | `ManagementPort`, `SecurityConfig`, network-policies.yaml |
| Secrets | Only from environment/secret store; no default admin credentials in production. Every environment except local (`BROKERVERSE_ENVIRONMENT` other than `local`, or the `prod` profile) refuses to start without the database credentials, a strong JWT key, the second-factor key, the mail and Valkey/Kafka credentials when in use, the single sign-on client secret when configured, the allowed origins and the password reset page (not localhost) and the mail sender; development values are refused. The seed profile has no key defaults | `ProductionSafeguards`, CONFIGURATION.md |
| Logging | CR/LF neutralised (log forging); no passwords in logs (`toString` masked) | application.yml, DTOs |
| Static analysis | SpotBugs + FindSecBugs, SAST, SonarJS | CI pipeline |
| Containers | Both images run as a non-root user: the backend as `brokerverse` (JRE alpine), the frontend as the unprivileged nginx user listening on port 8080; health checks on both; minimal alpine base images | `backend/Dockerfile`, `frontend/Dockerfile` |

## Licences and support of the platform components

Every platform component is open source under a licence that allows commercial use without a licence fee; none is
under a source-available licence (Valkey replaces Redis for this reason, client decision 08-Oct-2026). Each
component stays within the support window its upstream project publishes, so security fixes keep coming.

| Component | Version baseline | Licence | Function |
|---|---|---|---|
| PostgreSQL | 16.x | PostgreSQL Licence | Relational data store |
| Valkey | 8.x | BSD-3-Clause | Cache, job locks, token deny-list, counters |
| Apache Kafka | 3.9 (KRaft) | Apache 2.0 | Event streaming, transactional outbox |
| OpenJDK (Eclipse Temurin) | 21 LTS | GPLv2 with Classpath Exception | Application runtime |
| Spring Boot | 3.5.x | Apache 2.0 | Application framework |
| React | 19.x | MIT | Web user interface |
| Node.js | 22 LTS | MIT | Build of the web user interface (not a production runtime) |
| nginx (unprivileged image) | 1.30 | BSD-2-Clause | Serves the web user interface, proxies the API |
| Kubernetes (managed) | Provider-supported version | Apache 2.0 | Container orchestration |
| Gateway API controller | Gateway API v1 controller: the managed provider's controller or Envoy Gateway | Apache 2.0 | Ingress and traffic routing |

Support end dates and the annual review (also before go-live): [`DEPLOYMENT.md`](../operations/DEPLOYMENT.md)
section 7. A component that reaches its support end within the following twelve months is planned for upgrade; the
container images are rebuilt on patched base images and scanned (Trivy) before each release.

Reporting a vulnerability: contact the IortaTechNXT security team; do not open public issues.
